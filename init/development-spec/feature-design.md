# 캡처·녹화 기능 설계

[개발 명세 목차](README.md) · 설계 명세 v1.1 · 구현 및 실기 검증 전

## 6. 기능 구현 상세

### 6.1 OBS 연결

공식 5.x의 Hello → Identify → Identified 절차를 구현한다. 인증이 필수인지 확인하고 공식 SHA-256 챌린지 방식을 사용한다. JSON 서브프로토콜, RPC 버전 협상, 요청 ID 일치, 응답 성공 상태를 확인한다. 제어 연결에서는 녹화 출력 이벤트를 구독하고 상태 조회와 교차 검증한다. PNG 전용 연결은 같은 루프백 주소로 승인당 하나만 열며, 캡처 RPC 종결 즉시 닫는다. 제어 메시지 한도는 1 MiB, PNG 메시지 한도는 44 MiB다. 메시지 큐와 요청 타임아웃에도 검증한 고정 상한을 적용한다. 프록시·리다이렉트·압축을 비활성화하고, 클라이언트 버전이 설정을 지원하는지 확인한다. stdout에는 MCP 메시지만, 로그는 제한된 stderr 또는 로컬 감사 파일에 출력한다.

### 6.2 장면과 캡처 대상

사용자는 `AI Capture` 전용 프로필·장면 컬렉션을 만들고 허용 장면에 창 캡처 또는 특정 창 모드의 게임 캡처 한 개를 등록한다. 승인 정책은 OBS 장면·소스 식별자(UUID 지원 시 우선), 입력 종류, 창 매칭 설정을 고정한다. OBS 장면은 승인된 소스 하나가 켜져 있어야 한다. 중첩 장면, 그룹, 미검증 필터와 추가 입력은 거부한다.

OBS 설정 검증과 실제 Windows 창 확인을 각각 수행한다. OBS의 제목 일치 우선순위를 고정하고, 등록할 때 확인한 정확한 제목·클래스·실행 파일 절대 경로를 Windows에서 조회한다. OBS가 선택할 수 있는 같은 제목의 창이 복수이거나 창이 최소화·종료·변경되어 식별을 확정할 수 없으면 거부한다. 승인 화면에는 사용자가 OBS의 실제 화면을 로컬에서 확인하는 단계가 있다. 승인 직전과 직후, PNG 결과 수신 후 저장 직전, 녹화 감시 주기에 창 핸들·프로세스 식별값과 설정을 대조한다. 설정값과 Windows 창 조회만으로 OBS가 실제 사용 중인 창을 완전히 증명하기 어려우므로, 실기에서 대상과 미리보기를 확인하고 확정할 수 없는 캡처 모드는 사용 범위에서 제외한다.

장면 전환은 `obs_select_target`으로 승인받아 수행한다. 전용 컬렉션에서 유효 전환은 Cut으로 고정하고, 장면별 전환 재정의가 없는지 확인한다. `SetCurrentProgramScene` 후 3초 안에 `GetCurrentProgramScene`의 실제 ID와 `GetCurrentSceneTransitionCursor`의 비활성 상태를 확인한다. 상태가 어긋나거나 제한 시간이 지나면 `TARGET_CHANGED`를 반환한다. 캡처나 녹화 직전에도 최종 프로그램 장면·소스·창·방송·가상 카메라를 다시 확인한다. 이미 활성인 녹화 중 PNG를 허용하는 경우, 확인된 MCP 소유 세션의 동일 대상에만 새 승인을 받아 실행한다.

오디오는 기본 무음이다. 전용 프로필의 Desktop Audio·Mic/Aux·별도 오디오 입력을 비활성화하고, 창 캡처 오디오 옵션과 트랙 설정을 점검한다. 오디오 안전 상태를 확정할 수 없으면 시작을 거부한다. 예상과 다른 창이 검출돼도 전체 화면이나 다른 창으로 전환하지 않는다.

### 6.3 스크린샷

1. 허용 대상과 프로필·장면을 재검증하고 로컬 사용자 승인 후 다시 상태를 확인한다.
2. 같은 루프백의 PNG 전용 연결에서 `GetSourceScreenshot`에 승인된 sourceName/UUID, `imageFormat=png`, 제한된 크기만 전달한다. 1회에 캡처 하나만 처리한다. 제어 연결과 녹화 감시의 수신·디코딩·저장 시간을 분리한다.
3. 44 MiB WebSocket 메시지 한도를 적용한다. 32 MiB PNG의 Base64 길이는 약 42.7 MiB이므로 JSON 오버헤드를 수용한다. 디코딩 전에 Base64 길이가 `4 × ceil(32 MiB / 3)` 이하인지 검사하고, 디코딩 바이트 길이도 제한한다. data URI·MIME·Base64·PNG 서명과 파일 무결성을 확인하고, 가로·세로는 각각 최대 4096 픽셀로 제한한다. 크기 초과나 손상은 저장 없이 거부하고 PNG 연결만 닫는다.
4. 프로그램 장면과 승인 창의 상태를 저장 직전에 다시 확인한다. 서버가 생성한 파일명을 사용해 지정 디렉터리에 배타 저장하고 파일 크기·유효성을 확인한다. `SaveSourceScreenshot`을 사용해 OBS에 임의 경로를 직접 전달하지 않는다.
5. MCP 응답에는 메타데이터만 포함한다. 이미지 자체를 AI에 반환하거나 업로드하는 기능은 기본 제외한다. 사용자가 별도로 파일을 열거나 에이전트에 제공하면 해당 AI 서비스로 콘텐츠가 전달될 수 있다.

### 6.4 녹화 상태 머신

```text
IDLE → APPROVAL → STARTING → RECORDING ↔ PAUSED
                                  │          │
                                  └──→ STOPPING → FINALIZING → FINISHED
제어 연결 손실 / 이벤트 유실 / 상태 불일치 → UNKNOWN → 상태 조회 / 수동 확인
```

- **소유권 부여.** 시작 직전 연결과 `GetRecordStatus`의 비활성 상태를 확인하고, 승인된 요청을 한 번 송신한다. 같은 제어 연결에서 해당 `StartRecord`의 성공 응답, 이후의 `RecordStateChanged` 시작 상태, 활성 상태 조회가 모순 없이 이어질 때만 소유 세션으로 확정한다. 응답과 이벤트는 도착 순서가 바뀔 수 있으므로 송신 시점부터 모두 관찰한다. OBS 이벤트에 MCP 세션 ID가 없으므로 관찰이 이어지는 동안만 소유권을 인정한다. 전용 프로필을 사용하는 동안 수동 또는 다른 도구의 녹화 시작을 금지하며, 애매한 이벤트는 소유로 간주하지 않는다.
- **일시정지와 감시.** 소유권이 확인된 세션에만 `PauseRecord`와 `ResumeRecord`를 사용하며 출력 형식이 이를 지원하지 않으면 명시적으로 오류를 반환한다. 시작 요청 송신부터 단조 시계로 흐른 시간을 계산한다. 일시정지 시간도 포함하고 재개 시 마감은 그대로 유지한다. 1초마다 `GetRecordStatus.outputBytes`, 녹화 볼륨 여유 공간, 장면·창·출력 프로필과 안전 상태를 확인한다. 시간 도달, 출력 2 GiB 이상 또는 여유 공간 1 GiB 이하에서 소유 녹화만 중지한다. `outputBytes`는 출력량이므로 실제 MKV 크기는 종료 후 확인한다. OBS 응답·인코더 버퍼·감시 간격으로 생긴 초과는 기록한다.
- **종료와 파일 확인.** 사용자 요청, 자동 중지, 정상 서버 종료는 같은 중지 절차를 사용한다. 같은 세션을 연속 관찰한 `STOPPED` 이벤트 또는 현재 중지 요청의 응답에서 `outputPath`를 얻는다. 둘 다 수신하고 서로 다르면 결과를 확정하지 않는다. 비활성 상태를 확인하고 [파일 안전성 정책](security-requirements.md#43-파일-안전성-windows)의 새 MKV 검증을 수행한다. 수동 OBS 종료도 동일 세션의 종료가 연속 관찰되면 `OBS_STOPPED`로 기록한다. 파일 검증은 최대 5초 동안 수행하고 크기 안정화·읽기 가능 여부를 확인한다. 재생 검사를 수행하지 않았다면 `playback_verified=false`로 반환한다.
- **결과 재조회.** 완료 결과와 파일 검증 실패를 세션 ID로 키를 지정해 전용 로컬 디렉터리에 원자적으로 기록한다. 24시간 동안 최대 100건을 유지하고 가장 오래된 항목부터 만료한다. 절대 경로나 OBS 원본 응답은 기록하지 않는다. 종료 뒤 `obs_record_status(session_id)`와 같은 ID의 `obs_record_stop`은 보관된 결과를 반환한다. 중지 진행 중 중복 호출은 진행 상태를 반환하며 두 번째 중지 RPC를 발행하지 않는다. 재실행 시 완료 결과만 불러오고 활성 녹화의 소유권은 복원하지 않는다.
- **불확실한 상태.** 연결 단절·이벤트 유실·응답 타임아웃·모순을 감지하면 `STATE_UNKNOWN`으로 전환한다. 상태 조회만 허용하고 시작·일시정지·재개·자동 중지 RPC는 보류한다. 예상치 못한 종료 또는 새 시작이 관찰되면 이전 세션의 제어권을 폐기한다. 재연결 후 활성 녹화의 소유권을 자동 복구하지 않고 OBS에서 수동 확인·종료하도록 안내한다. 녹화가 비활성이고 정책 재검증이 끝나면 새 사용자 승인을 받아 새 세션을 시작할 수 있다. `StopRecord` 응답이 유실됐더라도 단절 없이 해당 녹화의 종료 이벤트가 확인되면 그 경로로 파일을 검증할 수 있다. 상태 변경 RPC를 재송신하지 않는다.
- **프로세스 종료.** 정상 종료 시 소유가 확인된 녹화만 정지한다. 강제 종료·PC 장애·연결 손실 중에는 녹화가 지속될 수 있어 OBS의 수동 종료 버튼을 안내한다. 프로세스 종료 뒤에도 자동 정지가 필수라면 OBS 출력의 동일성을 독립적으로 확인하는 신뢰된 별도 감시 프로세스를 차기 버전에서 설계하고 실기 검증한다.

### 6.5 동시성

Codex와 Claude Code에 동일 MCP를 등록할 수 있지만, v1은 한 번에 하나의 활성 MCP 서버가 OBS를 제어한다. Windows 사용자/OBS 인스턴스별 named mutex 등 검토된 OS 동기화 수단으로 서버 수명 전체에 걸친 단일 제어권을 보장한다. 두 번째 서버는 명확한 `BUSY` 또는 초기화 오류를 반환한다. 한 프로세스 안의 상태 변경과 송신은 짧은 임계 구역에서 직렬화한다. 사용자 승인 대기, 전환 완료 대기, PNG 송수신·검증, 파일 안정화 중에는 녹화 감시가 진행되도록 한다. 동시 클라이언트 지원은 공유 로컬 브로커 설계 및 별도 보안 검토 후 확장한다.
